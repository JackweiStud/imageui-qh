# 图片存储集成产品需求文档 (PRD)

**版本**: v1.0  
**状态**: 已完成 (Implemented)  
**更新日期**: 2025-12-09

## 1. 背景与目标
为了解决 MVP 阶段在 Vercel Serverless 环境下遇到的传输限制与稳定性问题，本项目决定重构图片传输层。将原本基于 "Base64 直接传输" 的架构升级为 "基于云存储 URL 引用传输" 的架构，以确保多图生成的稳定性并降低服务端内存压力。

## 2. 问题陈述 (Pain Points)
*   **Payload 限制**: Vercel Serverless Function 限制请求体最大 4.5MB。在 "Custom Swap" 模式下需上传 3 张图片，Base64 编码后极易触发 `413 Payload Too Large` 错误。
*   **内存溢出风险**: Base64 字符串占用内存大（比二进制大 33%），高并发下易导致 Node.js 进程 OOM (Out Of Memory)。
*   **超时风险**: 大文件传输占用了宝贵的 Serverless 执行时间 (Hobby Plan 仅 10s)，导致 `504 Gateway Timeout`。
*   **数据易失性**: 生成的图片仅存在于内存或临时响应中，缺乏持久化存储，用户刷新即丢失。

## 3. 解决方案架构 (Architecture)

采用 **Supabase Storage** 作为中间介质，API 交互仅传递文件的 **URL 引用**。

### 3.1 核心数据流 (Data Flow)
1.  **Frontend**: 用户选择图片 -> 上传至 Supabase `raw_uploads` 桶 -> 获取短期带签名 URL。
2.  **Frontend**: 调用 `/api/generate` 接口，Payload 仅包含图片 URL。
3.  **Backend**: 
    *   接收 URL 并进行 **SSRF 安全检查**。
    *   下载图片流 -> 转发给 Gemini AI 模型。
4.  **Backend**: 
    *   接收 AI 生成结果 (Buffer)。
    *   上传至 Supabase `generated_results` 桶。
    *   获取结果图的 Signed URL。
5.  **Frontend**: 接收结果 URL -> 展示并渲染。

## 4. 功能需求 (Detailed Requirements)

### 4.1 存储桶规划 (Bucket Configuration)
需要在 Supabase Storage 中创建以下两个 Bucket：

| Bucket Name | 用途 | 访问权限 (Privacy) | RLS 策略 | 生命周期 |
| :--- | :--- | :--- | :--- | :--- |
| `raw_uploads` | 用户上传素材 | Private | `INSERT`: 仅认证用户可上传至 `uid/*`<br>`SELECT`: 仅认证用户可读自己文件 | 建议开启 (24h 自动清理) |
| `generated_results` | AI 生成结果 | Private | `INSERT`: 仅后端 (Service Role) 可写<br>`SELECT`: 认证用户可读 | 永久保存 (或按需清理) |

### 4.2 前端改造 (`lib/api-client.ts`)
*   **上传封装**: 实现 `uploadImageToSupabase` 函数，支持将 Base64/Blob 并发上传。
*   **请求重构**: 所有生成函数 (`generateStyleTransform` 等) 在调用 API 前，必须先完成图片上传并将参数替换为 URL。

### 4.3 后端改造 (`app/api/generate/route.ts`)
*   **URL 兼容**: 修改入参类型定义，支持 URL 字符串。
*   **流式下载**: 实现 `fetchAndConvertToBase64`，将 URL 转回 Gemini 需要的格式。
*   **SSRF 防护 (P0 安全项)**: 
    *   **逻辑**: 在下载图片前，强制校验 URL 的 Hostname。
    *   **白名单**: 仅允许 `NEXT_PUBLIC_SUPABASE_URL` 对应的域名，或以 `.supabase.co` 结尾的域名。
    *   **目的**: 防止恶意用户传入内网地址 (如 `http://localhost:3000/env`) 窃取服务器敏感信息。
*   **结果持久化**: 生成成功后，通过 `SUPABASE_SERVICE_ROLE_KEY` 将结果回传至 `generated_results`，返回长效 Signed URL (24h)。

## 5. 环境变量与配置
为支持该功能，需确保以下环境变量配置正确：

*   `NEXT_PUBLIC_SUPABASE_URL`: (公开) Supabase 项目地址。
*   `NEXT_PUBLIC_SUPABASE_ANON_KEY`: (公开) 前端鉴权 Key。
*   **`SUPABASE_SERVICE_ROLE_KEY`**: (私密) **新增项**。用于后端绕过 RLS 写入结果桶。

## 6. 性能与选型分析 (Analysis)

### 6.1 为什么选择 Supabase Storage? (vs Cloudflare R2)
*   **优势**: 
    *   **开发速度**: 项目已集成 Supabase Auth，Storage 可直接复用鉴权系统 (RLS)，无需额外开发 Token 验证逻辑。
    *   **维护性**: 用户管理、数据库、文件存储在同一控制台，极大降低运维复杂度。
*   **缺点**: 有流量费用 (超过 5GB/月)。
*   **决策**: **MVP 阶段首选 Supabase**。未来用户量级破万、带宽成本敏感时，可迁移至 Cloudflare R2 (需自建鉴权层)。

### 6.2 延迟分析 (Latency)
*   **现状**: 虽然引入了 "上传" 和 "下载" 的额外 RTT (Round Trip Time)。
*   **评估**: 
    *   二进制上传比 Base64 文本传输体积小 33%。
    *   Vercel 与 Supabase (AWS) 之间的数据中心骨干网带宽极高。
*   **结论**: 端到端总耗时预计增加 < 500ms，但**任务成功率从 ~60% 提升至 99.9%**，用户体验显著提升。

## 7. 验收标准 (Acceptance Criteria)
1.  [x] **上传成功**: 前端可上传 3 张高清图而不报错。
2.  [x] **安全防护**: 后端拒绝非 Supabase域名的图片链接 (SSRF 测试通过)。
3.  [x] **结果留存**: Supabase 后台 `generated_results` 桶中能看到 AI 生成的历史图片。
4.  [x] **鉴权隔离**: 未登录用户无法上传文件。
